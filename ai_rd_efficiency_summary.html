1.2 业务愿景与 PDCA 闭环

希望通过销售任务，让销售巡店有重点，让管理有抓手。

传统外勤巡店往往「去了但不知道重点在哪」，管理层也缺乏可量化的跟进手段。sls-sales-task 将销售动作拆解为可配置、可下发、可追踪、可复盘的任务体系：总部/区域制定任务包并圈选门店群（或人员群），一线销售在外勤 App 中按任务清单执行，管理者实时查看完成进度与异常，周期结束后基于数据复盘优化下一轮策略。

系统设计上对标 PDCA 管理循环，覆盖销售动作管理全生命周期：

P

制定任务

Plan · 计划

配置数据模板、任务包/任务组与规则，圈选下发对象群，设定完成条件与截止时间

task_definition task_rule biz_template
D

执行任务

Do · 执行

下发明细触达门店/人员，外勤端按清单逐项完成，Groovy 脚本与对象群条件自动判定

task_distribution_detail task_instance
C

监控任务

Check · 检查

每日查看执行趋势与完成/反馈率，下钻战区与任务包表现，为下一轮任务配置提供依据

listStats feedback statistics
A

复盘任务

Act · 改进

基于执行明细与统计看板复盘，优化下一轮任务规划与下发策略

statistics execution_log

监控任务 · 任务统计看板（1.3 执行分析）

C 阶段（Check）的价值在于：运营与管理者可以每天打开销售任务中心 / 任务统计，按架构、月份、任务对象（如门店）筛选，跟踪执行趋势（完成率 / 反馈率折线）与任务状态分布——而不是等到周期结束才看结果。 当发现某类场景或任务包完成率持续偏低时，即可在下一轮制定任务（P）时做针对性调整：换圈选对象、改完成条件、增删任务项或切换下发策略，形成 C → P 的数据驱动闭环。

  • 执行趋势：按日观察完成率爬坡与反馈率变化，识别执行拐点（示例：7 月下旬完成率快速上升）。
  • 类型与状态：任务类型占比（综合队列 / 销售订单等）+ 已完成 / 已过期分布，判断哪类场景需加强。
  • 组织 & 任务包下钻：各战区任务量与完成率对比；任务包维度按完成率排序，定位「7 月利刃」等低完成包并调整配置。

1.3 核心业务链路

1
biz_template_config数据模板 — 定义数据源结构与事件规则，指标/外部数据进入任务体系的前置层
2
task_definition任务包 PACKAGE + 子任务 TASK + 动作 ACTION（1.4 起引入任务组 task_group）
3

4

5
task_instance + 统计/反馈实例条件匹配、执行分析看板、未完成反馈 — 支撑 C/A 阶段

完整模块说明见 doc/README.md；本文档侧重 AI 协作流程，不展开全部 API 细节。

1.4 AI Native 协作背景

  • 技术特征：模块多、Job 多、Groovy/CRON/分群规则复杂，文档与代码需强同步；从 MVP 到 1.4 共 5 个 PRD 版本、655 次 commit。
  • AI Native 动因：短周期交付模板/规则/明细/实例/统计等多模块；传统 TRD→编码→测试文档串行耗时长，边界（财季末月、DELAY、list N+1）易漏。
  • 核心策略：写代码前配置 Cursor Rules，强制「改代码必须联动 *_test_spec.md」；1.4 起采用任务清单 + Rules编排（见 §05）。
  • Token 换吞吐：3–5 月约 21 亿 token 支撑 0→1 主体研发与文档同步，人工重心转向需求确认、Review 与联调验收。

5.3 为何尚未直接接入 Hook

结论：Hook 适合在「自动化测试 + CI 门禁」成熟后叠加；当前项目测试自动化环节薄弱，先跑通任务清单 + Rules 的人工编排更稳。
✓ 已落地 · 任务清单 + Rules
  • *-tasks.md 按 id 追踪 pending / completed，方案与 acceptance 前置
  • Cursor Rules 约束分层、判空、分页、spec 同步等编码规范
  • 验收靠 *_test_spec.md JSON 示例 + 开发者 CURL / 联调
  • 首轮可推进 40–60% 骨架，框架内微调（见 §7.3）
○ 未接入 · Plan + Hook + 自动化用例
  • sessionStart Hook 自动扫描 pending 任务并 inject spec——缺少测试兜底时，误改难以及早发现
  • 无成熟单元 / 集成测试 CI；Job、Groovy、分群等路径难以机器回归
  • Hook 触发后 Agent 连续改多文件，若无 green build 门禁，放大错误扩散风险
  • 待测试基建补齐后，再叠 Hook 可达 §7.3 目标态 60–90%

演进顺序：对话式（MVP～1.2） → 任务清单 + Rules（当前） → Hook + 自动化测试（下一步）。Hook 不是不做，而是等「改了能自动验」的前提成立后再接。

06

Rules 与 Spec 联动实践

本项目最核心的提效经验：在写第一行业务代码之前先把 Rules 配好——尤其是「改代码必须联动修改对应 md」， 使 Agent 产出始终携带 test_spec 变更说明、JSON 示例与回归用例，联调与交接成本显著下降。

分层规范

Controller 薄层；业务在 Service 接口+实现；Job 委托 *JobServiceImpl，不在 Handler 写大段逻辑。

判空与 import

对象 Objects.nonNull；集合 CollectionUtils；字符串 StringUtils；禁止行内全限定名。

分页与 DTO

POST 默认 page=1, pageSize=20；列表返回 PageResult；DTO 字段加中文注释。

DDL 累计

表变更追加 doc/sql/update_tables.sql（及 dpc 侧同步）；spec 顶部写变更说明。

测试文档

doc/[模块]_test_spec.md；请求/响应 JSON 每字段 // 注释；fix 必补回归用例。

前端消费 spec

前端直接读后端 test_spec / api_spec 联调，减少口头传字段；1.4 起推进中文 spec 文件名。

有 Rule vs 无 Rule

❌ 无 Rules · 纯对话
  • 每轮对话风格不一致，分页/判空/分层随机
  • 改 Java 不改 spec，联调靠猜字段
  • DDL 遗漏审计字段，部署对不上实体
  • 后续对话常「改 A 坏 B」，无全局任务队列
✓ Rules + test_spec 联动
  • Agent 默认遵循 PageResult、Service 分层、git add 新文件
  • 同一 PR 内 spec 与代码同步，Postman 可直接抄 JSON
  • update_tables.sql 与 spec 变更说明成对出现
  • 任务清单 YAML（TGR/TPS）可标记 pending → completed

09

演进方向与风险

视角覆盖模型 · 产品 ⊂ 研发 ⊂ 测试

三个环节不是接力替换，而是包含关系：研发必须把产品口径装进去，测试必须把研发实现（以及其中的产品口径）装进去。 后一环节若只站在自己的位置上看，覆盖必然缺一层——一个人从头做到尾会有视角缺失，即便是 AI，目前也无法覆盖到这么细致。

产品⊂ 研发⊂ 测试 后一环节 ⊃ 前一环节 · 必须覆盖，不能替换
测

测试

独立视角：怎么验、是否做对 / 做完
必须覆盖研发（⊃ 产品）
异常路径 回归口径 验收门禁 「做完」可判定
⊃ 包裹研发 · 测的是实现，不是自己以为的功能

研发

独立视角：怎么做、边界与一致性
必须覆盖产品
方案边界 接口 / 数据一致性 实现约束
⊃ 包裹产品 · 能跑 ≠ 口径对
产

图 · 视角包含关系：每一环的「独立视角」长在外圈，内圈是必须吃透的前一环节——缺环则覆盖失败。

一人全做 → 视角塌缩

后一环节用的是自己刚写完的那双眼，无法真正「覆盖」前一环节。产品想清楚了 ≠ 研发边界清了 ≠ 测试能验收。

盲区 · 口径漂移 盲区 · 实现边界 盲区 · 异常路径
仅靠 AI → 同样盖不住三层细致度

AI 能加速草稿与编码，但一次会话很难同时维持产品口径、实现约束、验收门禁三套独立视角。复杂规则仍需分角色 Review——这也是演进上要走 PRD → TRD → test_spec 闭环、而不是「一个人 + 一个 Agent 包办」的原因。

盲区 · 验收口径 盲区 · 回归遗漏 盲区 · 角色自检失效

下一步

  • 补齐测试自动化：单元 / 集成测试 + CI green 门禁——Hook 的前置条件（当前环节薄弱，故未直接接入）
  • Plan + Hook：测试基建就绪后，sessionStart 扫描 doc/*-tasks.md，自动注入 pending 任务与 spec_target
  • Spec 索引：spec-index.json 映射前端 route → 后端 spec 章节，Hook 替代手动 @
  • 产品 → TRD → test_spec 闭环：PRD md 结构化，Agent 生成 TRD 骨架与 QA 用例对账
  • 专属 Agent：整合 Rules + 任务队列 + md 验收，形成项目级长期记忆

风险

  • 纯对话式缺少全局编排，后续改动可能破坏已完成模块——需任务清单与 acceptance 约束
  • 一人包办产品 / 研发 / 测试，或仅靠 AI 会话闭环：后一环节无法真正覆盖前一环节视角，口径漂移与验收盲区不可避免——即便是 AI，目前也无法覆盖到三层独立视角的细致度
  • Token 成本需与人力节省平衡；复杂方案仍依赖人工 Review，不可全自动上线
  • 多仓库协作（后端 sls-sales-task + 前端 Comm-Divisor-Service）需统一 spec 命名与版本口径
