1.2 业务愿景与 PDCA 闭环

希望通过销售任务，让销售巡店有重点，让管理有抓手。

传统外勤巡店往往「去了但不知道重点在哪」，管理层也缺乏可量化的跟进手段。sls-sales-task 将销售动作拆解为可配置、可下发、可追踪、可复盘的任务体系：总部/区域制定任务包并圈选门店群（或人员群），一线销售在外勤 App 中按任务清单执行，管理者实时查看完成进度与异常，周期结束后基于数据复盘优化下一轮策略。

系统设计上对标 PDCA 管理循环，覆盖销售动作管理全生命周期：

制定任务

Plan · 计划

配置数据模板、任务包/任务组与规则，圈选下发对象群，设定完成条件与截止时间

task_definition task_rule biz_template
D

执行任务

Do · 执行

下发明细触达门店/人员，外勤端按清单逐项完成，Groovy 脚本与对象群条件自动判定

监控任务 · 任务统计看板（1.3 执行分析）

C 阶段（Check）的价值在于：运营与管理者可以每天打开销售任务中心 / 任务统计，按架构、月份、任务对象（如门店）筛选，跟踪执行趋势（完成率 / 反馈率折线）与任务状态分布——而不是等到周期结束才看结果。 当发现某类场景或任务包完成率持续偏低时，即可在下一轮制定任务（P）时做针对性调整：换圈选对象、改完成条件、增删任务项或切换下发策略，形成 C → P 的数据驱动闭环。

  • 执行趋势：按日观察完成率爬坡与反馈率变化，识别执行拐点（示例：7 月下旬完成率快速上升）。
  • 类型与状态：任务类型占比（综合队列 / 销售订单等）+ 已完成 / 已过期分布，判断哪类场景需加强。
  • 组织 & 任务包下钻：各战区任务量与完成率对比；任务包维度按完成率排序，定位「7 月利刃」等低完成包并调整配置。

1.3 核心业务链路

1
biz_template_config数据模板 — 定义数据源结构与事件规则，指标/外部数据进入任务体系的前置层
2
task_definition任务包 PACKAGE + 子任务 TASK + 动作 ACTION（1.4 起引入任务组 task_group）
3

4

5
task_instance + 统计/反馈实例条件匹配、执行分析看板、未完成反馈 — 支撑 C/A 阶段

完整模块说明见 doc/README.md；本文档侧重 AI 协作流程，不展开全部 API 细节。

1.4 AI Native 协作背景

  • 技术特征：模块多、Job 多、Groovy/CRON/分群规则复杂，文档与代码需强同步。产品 PRD 共 5 版（MVP→1.4，1.4 主干已合入）；代码继续到 feature/202610_op，累计 726 次 commit。
  • AI Native 动因：短周期交付模板/规则/明细/实例/统计等多模块；传统 TRD→编码→测试文档串行耗时长，边界（财季末月、DELAY、list N+1）易漏。
  • 核心策略：写代码前配置 Cursor Rules，强制「改代码必须联动 *_test_spec.md」；1.4 起采用任务清单 + Rules编排（见 §05）。
  • Token 换吞吐：3–5 月约 21 亿 token 支撑 0→1；截止当前版本累计约 40 亿。人工重心转向需求确认、Review 与联调验收。

模块引入版本功能介绍
condition_repo + task_template MVP 条件库沉淀可复用的完成条件片段，和模板字段、Groovy 脚本组合后挂到任务上。任务模版独立成表，把常用的对象、执行类型和完成脚本存成模板，新建任务时直接复用，避免每次从空白配置。应用端 H5 按任务详情读取这套条件结果。
task_definition + task_rule MVP → 1.2 任务定义分三层：任务包 PACKAGE、子任务 TASK、动作 ACTION。createPackage 一次创建包和子任务，并绑定数据模板与规则。规则覆盖手动 / CRON / 固定时间下发、完成判定、截止时间（按月、相对天数、财季末月），秒位归 59。1.2 补齐编码规则、复制、立即下发、已下发后部分字段可改，以及门店 / 人员 / 经销商对象。
task_distribution_detail MVP → 1.2 到达 distributed_at 后，按「任务包 + 子任务 + 目标实体」生成一线可见的任务清单，对象覆盖门店和人员。列表、导出、状态统计共用同一套筛选；XXL-JOB 负责就绪转进行中、到期完成、超 end_time 过期、分群同步和归属部门补全。状态为进行中、已完成、已关闭、已过期。截止 2026-11 已下发 700 万+。
biz_template + datasource 1.1 数据模板定义指标和外部事件怎么进任务体系，字段映射用 is_search_primary_key 标出列表和导出的搜索主键。类型支持 NUMBER / STRING / BOOLEAN / DATE，202608 起增加 EX 表达式。同时管理数据源连接、Kafka 事件数据集和试用数据，供完成条件与下发筛选取数。
groovy + dynamic_http 1.1 → 1.2 完成条件可以用 Groovy 脚本写，脚本实例支持启用、禁用和版本管理；调试接口提供 execute、executeMap、assembleMap。动态 HTTP 端点按分组配置外部指标接口，密钥脱敏，并支撑 DELAY 同步。脚本里的 @ 指令在保存和执行前做校验，避免引用不存在的字段或指令。
auth + op_permissions 1.2 页面迁入 OP 后，请求同时走 JWT 与 OP 两套拦截，白名单接口跳过校验。功能权限按管理员、总部、区域、业务等角色控制菜单和按钮，资源由定时任务从 OP 同步。统计部门树只返回账号真正有权限的部门，避免默认选中无权限祖先后接口被拦。
feedback + statistics 1.3 未完成任务可提交原因、修改反馈或直接关闭，明细列表能看到反馈说明。统计按日打快照，看板给出 KPI、完成率 / 反馈率趋势、任务类型占比，并下钻到战区和任务包。部门范围按登录人权限裁剪；末级组织按网点负责人汇总。快照由 TPS Job 刷新。
task_group 1.4 新建独立任务组表，编码前缀 RWZ，本身不下发，用来给多个任务包打策略标签。下发对象、节奏、去重从包层下沉到每个子任务：同组可以圈不同门店群，完成标准支持模板、自定义、对象群，对象群可按「在群 / 不在群」反向判定，去重增加「对象 + 下发时间」和月内不重复。
v2_tour_patrol_record 202608 消费巡店 topic，只处理 key 为 v2_tour_patrol_record 的消息。先把 tourPhotos 展平，再按 SKU code 调商品中心，把 pure_sku 的 epuCode 写回，并在最外层写入识别总数 skuNumer（code 去重）。补齐后走统一下发链路，用来判定巡店相关任务是否完成。同期还有设备 binlog 独立消费、任务组联动和进行中统计。
crowd sync + childrenList 202609 分群下发改为按批拉对象并写入明细，Redis 用占位和冷却 key 防止同一包被定时任务打重。任务定义的 childrenList 可以按任务组聚合，方便配置端按组查看子任务。创建实例若撞上 uk_task_code，只跳过冲突行，不再把整条 Kafka 消息丢掉。消费日志不再打印完整报文。
dept leader + IMMEDIATE 202610 明细列表的数据范围等于登录人默认部门，再加上其作为部门负责人管辖的部门；负责人通过 EHR 批量接口 fieldType=2 按 userId 查询。手动下发（distributionType=IMMEDIATE）只在点击时触发，定时分群 Job 会跳过，并使用独立 Redis key，避免冷却期内点不了手动下发。运行日志改为标准输出，不再落本地滚动文件。

  • Hook 触发后 Agent 连续改多文件，若无 green build 门禁，放大错误扩散风险
  • 待测试基建补齐后，再叠 Hook 可达 §7.3 目标态 60–90%

Rules 与 Spec 联动实践

本项目最核心的提效经验：在写第一行业务代码之前先把 Rules 配好——尤其是「改代码必须联动修改对应 md」， 使 Agent 产出始终携带 test_spec 变更说明、JSON 示例与回归用例，联调与交接成本显著下降。 查看 Rules 明细配置 →

分层规范

Controller 薄层；业务在 Service 接口+实现；Job 委托 *JobServiceImpl，不在 Handler 写大段逻辑。

判空与 import

对象 Objects.nonNull；集合 CollectionUtils；字符串 StringUtils；禁止行内全限定名。

分页与 DTO

POST 默认 page=1, pageSize=20；列表返回 PageResult；DTO 字段加中文注释。

DDL 累计

表变更追加 doc/sql/update_tables.sql（及 dpc 侧同步）；spec 顶部写变更说明。

测试文档

doc/[模块]_test_spec.md；请求/响应 JSON 每字段 // 注释；fix 必补回归用例。

前端消费 spec

前端直接读后端 test_spec / api_spec 联调，减少口头传字段；1.4 起推进中文 spec 文件名。

有 Rule vs 无 Rule

❌ 无 Rules · 纯对话
  • 每轮对话风格不一致，分页/判空/分层随机
  • 改 Java 不改 spec，联调靠猜字段
  • DDL 遗漏审计字段，部署对不上实体
  • 后续对话常「改 A 坏 B」，无全局任务队列
✓ Rules + test_spec 联动
  • Agent 默认遵循 PageResult、Service 分层、git add 新文件
  • 同一 PR 内 spec 与代码同步，Postman 可直接抄 JSON
  • update_tables.sql 与 spec 变更说明成对出现
  • 任务清单 YAML（TGR/TPS）可标记 pending → completed

  • Token 成本需与人力节省平衡；复杂方案仍依赖人工 Review，不可全自动上线
