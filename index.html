1.2 业务愿景与 PDCA 闭环

希望通过销售任务，让销售巡店有重点，让管理有抓手。

传统外勤巡店往往「去了但不知道重点在哪」，管理层也缺乏可量化的跟进手段。sls-sales-task 将销售动作拆解为可配置、可下发、可追踪、可复盘的任务体系：总部/区域制定任务包并圈选门店群，一线销售在外勤 App 中按任务清单执行，管理者实时查看完成进度与异常，周期结束后基于数据复盘优化下一轮策略。

⚙ 核心实践 · 最高优先级

提前设置 Rules：AI 协作的「宪法」

AI 生成代码的能力很强，但默认不会主动维护文档——除非你提前用 Rules 把它写进「必须遵守的契约」。 本项目在启动之初即在 Cursor User Rules 中固化约束，其中最关键的一条是： 代码逻辑变更时，必须同步更新 doc/ 下对应的 *_test_spec.md（功能变更改对应用例，Bug 修复补回归用例，表结构变更同步 dpc/sql）。 这不是形式主义，而是让 AI 协作从「一次性对话」变成「可沉淀、可复用、可交接」的工程过程。

1项目启动前写入分层、判空、分页、import 等编码规范
2第一个模块开写前约定 test_spec 命名、JSON 注释格式、变更说明写法
3每次需求AI 改 Java 的同时改 md + SQL，同一轮对话内完成
4Review 时以 spec 变更说明为审查入口，而非逐行读 ServiceImpl

「改代码联动改 MD」带来的实际好处

📜

过程结果留存，便于追溯

每次需求/修复都会在 spec 顶部留下「变更说明」，形成按时间叠加的决策日志。回看 git history 时，md 变更说明比 commit message 更完整地还原「为什么改」。

例：task_distribution_detail_test_spec.md 685 行，9 个 Job + 12+ API 全量留存，见下方典型范例
🔧

利于长期维护

业务逻辑散落在 3800 行的 ServiceImpl 中时，维护者必须读代码才能理解行为。spec 把「接口契约 + 边界规则 + 用例预期」结构化沉淀，改一处功能只需先读 spec 再定位代码。

例：list 的 1 万条截断、end_time 闭区间筛选规则全在 spec，不必读 TaskDistributionDetailServiceImpl
👥

降低交接与协作成本

新同学接手模块时，spec 即「可执行的说明书」：JSON 示例可直接导入 Postman，变更说明即 changelog。测试、前端、产品均可对照同一份文档，减少反复口头同步。

例：biz_template_config_controller_api_spec.md 与 Controller 字段级对齐，联调零猜测
🛡️

Bug 修复可回归、防复发

Rule 要求 fix 类改动必须补充回归用例。修复逻辑写入 spec 后，下次 AI 或人工改相关代码时，spec 中的回归场景会作为上下文被引用，避免同类问题反复出现。

例：用例 12a OR 匹配回归、用例 12e end_time 闭区间 fix，防止同类筛选 bug 复发
⚡

AI 上下文自增强

spec 越完整，AI 后续改动的上下文越准确。Rule 强制同步后，spec 始终反映最新行为，AI 不必猜测「当前接口到底支持哪些参数」，减少幻觉与漏改。

例：改 taskRule 的 CRON 周期 UI 解析时，AI 直接读 spec 中 distributionTimeConfig 结构，一次改对
✅

Review 与验收更高效

Reviewer 先看 spec 变更说明 + diff 中的 md 部分，即可判断影响范围是否完整（接口、Job、SQL 是否遗漏），不必从 Java diff 反推业务含义。

例：列表性能优化时，spec 明确 childTaskCount 改为批量聚合，Review 一眼确认无遗漏

改代码联动改 MD 最佳实践

这是本项目「改 Java 必改 md」最典型的模块文档。任务下发明细逻辑横跨 Controller、Service、多个 JobService、分群接口、DTS 补全、Redis 缓存——若只改代码不留 spec，3 个月后几乎无人能讲清「list 为什么只查最近 1 万条」「statusStats 与 statusStatsByListByPackage 有何区别」。该文件把梳理过程中的业务决策、边界规则、回归用例、性能口径全部固化下来。

文档结构与梳理细节
  • 顶部注明合并来源（多个旧 spec 归一），避免历史文档散落
  • 第一篇：明细触发、API、Action 同步 — 业务说明 + 定时任务清单 + 幂等去重
  • 第二篇：条件匹配 Job、实例评估 — Groovy 脚本与状态流转
  • 已删除的 Job（如 triggerTaskDistributionDetail）在 spec 中显式标注移除，防止 AI 或新人误引用
  • 每个 XXL-JOB 单独成用例：Handler 名、触发逻辑逐步编号、任务参数 JSON 示例
spec 中沉淀的核心内容
  • 9+ 个 API：create / detail / list / listByPackage / listGroupByTarget / export / statusStats 等
  • 请求 JSON 带 // 注释：如 list 接口 20+ 筛选字段及精准/OR/LIKE 语义
  • 复杂筛选规则文字化：如 startTimeFrom + endTimeFrom 同时有值时按 end_time 闭区间
  • 性能口径：list 先按 id 降序 LIMIT 10000 再分页；export 全量流式；代表行批量查询
  • 分群 Job 逐步逻辑：CAS 占位、500 批判重、200 Future 刷盘、DTS 补全、finally 释放槽位
  • Redis 缓存 key 与 TTL、降级策略均写入 spec
联动改 MD 的典型变更场景
  • 新增 owningDepartmentCodes 筛选 → spec 补充用例 12f + JSON 注释
  • list / listByPackage 性能优化 → spec 写「最近 1 万条」口径 + 索引说明
  • 合并过期 Job → spec 标注原 Job 已删除、新 Handler 合并逻辑
  • fix 目标 OR 匹配 bug → 补充用例 12a 回归说明
  • 新增 statusStatsByListByPackage → 完整请求/响应 JSON + 与 list 口径差异
  • 手动同步接口改异步 → spec 更新「立即返回 + 日志关键字」预期
梳理过程中解决的「隐性知识」
  • list 轻量 vs detail 全量：linkedTemplateDefinitionList 列表不返回
  • listByPackage 去重维度：task_package_id + target_entity_code，与 list 平铺不同
  • statusStats 全量统计 vs statusStatsByListByPackage 代表行统计，expiredCount 恒为 0
  • 唯一键 uk_task_pkg_def_target_code 与并发幂等关系
  • distribution_push_completed 与分群 Job 互斥的 CAS 语义
  • 仅 objectCode=STORE 时填充 lastVisitClosedTime

第一篇：明细触发、API 与 Action 同步

功能模块：任务下发明细触发
一、业务说明

遍历 TaskInstance 数据，判断任务包类型，在到达下发时间（distributed_at）时触发创建 task_distribution_detail。任务包下若有多个普通任务(TASK)，则为每个(任务包+普通任务+目标实体)创建一条明细，分别关联 task_package_id 和 task_def_id。

表字段 object_code：对象编码语义，与 task_definition.object_code 一致；接口返回 TaskDistributionDetailDTO 时带出 objectCode（表已无 object_type 列）。

二、定时任务
  • 原 XXL-JOB triggerTaskDistributionDetail（扫描 PENDING 实例并下发明细）已移除，对应 TaskDistributionTriggerService 已删除；本模块其余 Job 见 TaskDistributionDetailJob：syncPackageTaskStatusCompleted（内含 PACKAGE 完成态同步 + TASK 到期过期）、expireInProgressDetailsPastEndTime（按明细 end_time 全表批量过期进行中明细，可与前者分调度并存）、syncReadyPackagesAndTasksToInProgress、syncInProgressPackagesByCrowd、refreshInProgressPackageCronDistributedAt、completeInProgressDetailsByCrowdForCronCompletionJudgment（CRON 完成判断 + 分群 latest 批量明细完成）、scanInProgressTaskDelaySyncStrategy、syncTaskDistributionDetailOwningDepartment（补全归属部门与部门路径）、refreshTaskDistributionDetailStatusStatsCache（预热 statusStats / statusStatsByListByPackage 两处 Redis）等。
三、任务包解析
  • 用例2：任务包类型识别
    • 通过 task_rule_id → task_definition.rule_id（或 task_template_definition.rule_id）→ task_definition 解析
    • 若 task_def 的 task_type=PACKAGE，则视为任务包
    • 若 task_def 为 ACTION/TASK 且有 parent_id，则取父级为任务包
    • 预期：非任务包类型实例不触发明细创建
四、幂等与去重
  • 用例3：已下发明细的实例跳过
    • 若 task_distribution_detail 中已存在该 task_instance_id 的记录，则跳过创建

功能模块：任务下发明细条件匹配
一、变更说明

在执行 TaskDistributionDetailSyncService.evaluateInstanceMatchForInProgressDetails（及后续 evaluateConditionCalculationByInstance）时：

1. 从 task_result_data 解析出的 mappedResults 中选取目标实体编码时：除 isSearchPrimaryKey=true 外，还要求该条目的 objectCode 与当前 TASK 对应的 task_definition.object_code 一致（二者均为空视为一致）；否则不命中明细、不创建 task_instance。

2. 对每条参与匹配的 task_distribution_detail 先创建一条 task_instance。

3. task_instance 需要写入 source_data（Kafka 消息 value）、task_result_data（TaskDistributionTaskResult 序列化 JSON）以及关联的 task_distribution_detail_id。

4. 若该明细所有条件均 matched=true，则继续将明细状态推进为 COMPLETED。

5. TaskDistributionDetailSyncService.evaluateConditionCalculationByInstance(TaskInstanceDTO) 在完整跑通条件评估并返回结果后，若 task_instance.id 非空会将对应 task_instance.status 更新为 COMPLETED，并写入 completed_at（仅内存实例无 id 时跳过实例表更新）。

6. evaluateConditionCalculationByInstance 在 task_instance.id 非空时执行后会新增一条 task_instance_execution_log，通过 task_instance_id 与任务实例绑定，记录本次条件计算结果摘要（DELAY 扫描仅内存实例、无 id 时跳过写日志）；completion_script（Groovy）抛异常时仍会写日志（event_data 含 completionScriptException=true 及错误信息），且不会将 task_instance 置为已完成，便于下次重试；脚本正常执行（含返回 false）时仍按原逻辑置实例完成（同上，仅 id 非空时更新实例表）。

7. 完成判定唯一依据：evaluateConditionMatch 不再读取 condition_repo/不再做字段逐条对比；执行前按 task_definition.condition_ids 反查条件库明细列表，注入变量 conditionDetailList（与 testTaskWithConditionDetails 一致），再执行 task_definition.completion_script（Groovy 片段，返回布尔）。脚本参数另有：mappedResults（原始列表）、mappedResultMap（mapped_col -> mapped_col_val）。若 task_result_data 解析结果中带有 completionScriptData（如 DELAY 同步扫描将 DynamicHttp 解析结果写入 TaskDistributionTaskResult），则额外注入 Groovy 变量 data，与仅走 Kafka/映射结果、不带 completionScriptData 的链路兼容。仅 templateType=TARGET 时：先剥离 @ 行，再将脚本中 {{fieldCode}} 按 conditionDetailList 的 fieldCode 匹配，替换为对应 defaultValue 首个 value 的 Groovy 字面量（dataTypeDefinition=NUMBER 时转为 long 数字字面量，非字符串）；COMMON/TEMPORARY 不做占位替换。

8. DELAY 同步扫描回归（scanInProgressTaskDelaySyncStrategy / TaskInProgressDelaySyncStrategyScanJobServiceImpl）：仅处理绑定 templateType=TARGET 的进行中 TASK；COMMON/TEMPORARY 等非 TARGET 模板直接过滤跳过。TARGET 从子 TASK completion_script 的 @xxx(endpointId) 解析 dynamic_http_endpoint.id 后直接 invoke。对每个 targetEntityCode 首次拉数后调用 evaluateDelaySyncWithPersistedInstance；同一 targetEntityCode 复用布尔结果。明细按 id 游标每批最多 20000 条，判定缓存跨批复用。Job 参数可选 ids（任务包 task_definition.id 列表）：非空时仅扫描 parent_id 命中这些包 id 的子 TASK；支持 JSON {"maxScanCount":20000,"ids":[101]} 或逗号分隔 20000,101,102。

9. 返回值：conditionMatchResults 固定仅 1 条，ConditionRepoDTO.defaultValue/description 为脚本片段内容，matched=true/false 为脚本执行结果；同响应中携带 conditionDetailList（task_definition.condition_ids 反查条件库明细，与脚本注入变量一致）。

10. 新增 TaskDistributionDetailSyncService.evaluateScriptCompletionByInstance(TaskInstanceDTO)：基于实例中的 task_result_data 解析 mappedResults，按 taskDefId 查询 task_definition 与 task_rule；当 task_rule.completion_type=SCRIPT_BASED 时，执行 task_rule.completion_script（Groovy）并返回布尔结果。执行参数包含：mappedResults（原始列表）、mappedResultMap（mapped_col -> mapped_col_val）、taskResult、taskDefId、taskCode、taskExecutionEventCode。

分页接口 — 请求默认值 + 统一响应结构
规则原文

列表类的接口进行返回的包装，请求参数 post 中需要携带 page=1，pageSize=20 的默认参数，返回到时候，需要携带分页的明细，返回值举例：

{
  "code": 0,
  "message": "success",
  "data": {
    "records": [
      // 当前页数据列表
    ],
    "total": 7884, // 总条数
    "page": 1, // 当前页
    "pageSize": 20, // 每一页的条数
    "totalPage": 10 // 总页数
  }
}
详细说明：所有列表 POST 接口的请求 DTO 中 page / pageSize 须有默认值（1 和 20）；Service 返回 PageResult<T>，外层由统一 Response 包装。前端列表页可直接复用同一结构，无需每次对齐。
本项目举例 POST /sales/task/definition/list、POST /sales/task/biz/template/config/list 均遵循此结构；PageRequest 默认 page=1, pageSize=20。

分层架构 — Controller 薄 · Service 厚 · Job 委托
规则原文
  • 业务逻辑不要写在路由层，需要写在 service 层
  • service 必须先有接口层再创建实现层，实现层负责逻辑细节，实现层详细的添加注释
  • job 层也不要写太多的逻辑细节，需要提取到对应 JobService 里
详细说明：
  • Controller：只做参数接收、调用 Service、返回 Response，不写 if-else 业务分支
  • Service 接口 + 实现：接口定义契约，实现类承载全部业务逻辑，复杂校验、事务、外部调用均在此层；实现类方法加注释说明业务规则
  • Job + JobService：@XxlJob 方法只做调度入口，扫描/批处理/状态流转逻辑放 *JobServiceImpl
本项目举例 TaskDefinitionController.createPackage → TaskDefinitionServiceImpl（3800+ 行校验与创建逻辑）；TaskDistributionDetailJob 中 @XxlJob("syncInProgressPackagesByCrowd") → TaskDistributionDetailSyncServiceImpl。

❌ 现状 · 对话式
  • 需求通过自然语言在 Cursor 里逐条描述，上下文随对话滚动，容易遗漏边界
  • 同一功能不同开发者描述方式不同，AI 产出稳定性差异大

  rules = rulesLoader.forStack(task);    // backend.md / frontend.md

  agent.run({
    prompt: task.title,
    context: [specs, rules, relatedSourceFiles(task)],
    constraints: task.acceptance           // 验收清单作为硬约束
  });

  if (mdVerifier.check(task)) {          // md 即完成信号
    task.status = 'done_verified';
    plan.writeProgress();
  } else {
    agent.retry(missingItems);             // 补 spec / 补代码
  }
}
